# 汉兜评价算法设计与实现

本文是汉兜（Handle）评价模块的设计说明和开发文档。目标读者是已经了解汉兜基本玩法，但没有参与评价算法讨论的程序员。

阅读本文后，应当能够理解：

- 汉兜中的“好猜测”究竟指什么；
- 为什么不能简单按剩余成语数或逐元素加分；
- V1、V2、V3 和末盘模型分别解决了什么问题；
- 当前如何计算期望信息、实际信息、百分位和最终等级；
- 评价状态如何恢复、持久化以及在 Web Worker 中预计算；
- 当前模型有意忽略了哪些信息，以及修改算法时必须保持哪些不变量。

> 本文描述的是当前 `EVAL_VERSION = 5` 的实现。讨论中的“V2”“V3”是算法概念版本，不总是与 localStorage 中的持久化版本号一一对应。

## 1. 问题定义

汉兜要求玩家猜一个四字成语。每个字有五个反馈维度：

1. 汉字本身；
2. 声母；
3. 韵母；
4. 不带声调的全拼；
5. 声调。

每个维度都采用 Wordle 式反馈：

- 灰色（`none`）：答案中没有可与该查询匹配的元素；
- 红色（`misplaced`）：答案中存在该元素，但位置错误；
- 绿色（`exact`）：元素及位置都正确。

重复元素必须先匹配绿色，再将剩余查询从左到右匹配红色，多余重复项为灰色。评价算法的反馈编码必须与游戏的 `testAnswer()` 完全一致，否则后验会在若干轮后错误地删除真实答案。

评价的目标类似棋类网站的 move classification：每次提交后给出 `brilliant`、`excellent` 等等级。但汉兜与棋类的根本区别是谜底隐藏。评价要回答的不是“这次碰巧拿到了多少信息”，而是：

> 在提交前玩家已知的公开信息下，这个猜测平均能够区分多少种可能情况？

因此，普通评价主要衡量猜测的**期望信息增益**，而不是它针对当前真实谜底的运气。当前实现最终放弃了 `lucky/unlucky` 附加评价。

## 2. 从游戏直觉得到的关键结论

### 2.1 满足全部反馈不等于信息量最大

假设已知某个元素是绿色，再把它放回原位置，通常不会继续区分答案。相反，将红色元素移动到其它位置，或者查询高频但尚未出现的元素，更可能产生不同反馈。

因此，中前盘常见的好猜测会：

- 避免重复查询已确定的灰色元素；
- 将红色元素移动到尚未排除的位置；
- 避免无意义地重复绿色信息；
- 用剩余位置覆盖高频的新元素。

不过这些只能作为直觉，不能直接写成“移动一个红色加几分、复用一个绿色扣几分”的规则。重复元素、位置约束、合法拼音和全拼反馈会让固定权重迅速失效。

### 2.2 多个查询不是独立信息

例如，已知某个 `sh` 只能在第 2、3、4 位且三者等概率。在第 2、3 位各查询一次 `sh`，反馈只有：

- 绿、灰；
- 灰、绿；
- 红、灰。

三个结果直接确定位置，因此信息熵为：

\[
\log_2 3 \approx 1.585\text{ bit}
\]

它既不是单个 `sh` 查询信息量的两倍，也不能通过两个独立 Bernoulli 变量相加得到。重复元素更多时，独立性错误会更严重。

这正是当前算法必须按“四位置完整反馈码”分组，而不能逐元素计分的原因。

### 2.3 全拼不是第三个独立拼音维度

全拼由声母和韵母共同决定。绿色全拼通常只是确认已经知道的声韵组合；红色或灰色全拼则会补充“哪一个声母与哪一个韵母相连”的信息。

因此不能计算：

\[
H(F_I)+H(F_F)+H(F_{PY})
\]

这会重复计算共享信息。当前模型将三种反馈拼成一个联合反馈变量：

\[
E_1(g)=H(F_I(g,X),F_F(g,X),F_{PY}(g,X))
\]

### 2.4 “真实成语候选很少”不等于“人类掌握的信息已饱和”

44010 条语料只是现实成语的稀疏样本。一次反馈后，满足全部声母、韵母、全拼反馈的真实成语可能只剩一个，但从拼音逻辑上仍可能存在大量合理组合。

如果直接以真实候选集计算熵，会出现：

- 真实联合候选首猜后就降到个位数；
- 很多完全不同的第六猜都得到 `E1 = 0`；
- 算法错误地认为盘面已经没有未知信息。

所以真实成语库既是先验数据，也是一种有偏、稀疏的观测，不能在所有阶段直接当作完整假设空间。

### 2.5 当前信息量可以超过 `log2(44010)`

`log2(44010) ≈ 15.42 bit` 只表示“从 44010 个真实成语中选一个”的不确定性。评价模型跟踪的是声母、韵母、全拼、声调反馈所形成的逻辑条件；这些维度在模型中可以保留独立后验，累计条件信息 `J` 因而可能超过 15.42 bit。

这不是数学错误。`J` 的用途不是估计“还剩几条词典记录”，而是衡量公开反馈已经给玩家多少约束。

## 3. 设计目标

当前算法坚持四项原则：

- **定量**：先得到连续分数，再统一分档；
- **尽量客观**：避免手工规定“一个红色值多少分”；
- **可复现**：同一历史、猜测和配置必须得到相同粒子、分数和排名；
- **可交互**：计算不能阻塞输入和按钮，正常目标设备应在数秒内完成预计算。

它是评价器，不是求解器。算法只需要比较玩家猜测与固定基准猜测，不需要遍历 44010 个成语寻找全局最优解。

## 4. 算法迭代过程

### 4.1 初始方案：真实候选集的信息熵

最直接的方案是保留所有满足历史反馈的成语，对每个猜测统计反馈分布，再计算熵。它在 Wordle 中非常自然，但在汉兜中有两个致命问题：

1. 汉兜一次猜测的反馈维度非常多，真实候选集收缩得过快；
2. 候选只剩一条时，任何猜测的候选集熵都为零，但人类显然未必能推出答案。

因此，“剩余真实成语数量”没有成为当前信息量的定义。

### 4.2 V1：逐元素独立的期望信息

第一个 MVP 对声母、韵母逐元素估计出现概率，并把各元素的信息量相加。它依赖类似 `a.csv` 的频数表，并做了非常强的简化：

- 声母、韵母相互独立；
- 不考虑重复元素；
- 不考虑声调、全拼、汉字；
- 获取信息的主要方式是查询新元素和移动红色。

例如，语料中 33110 个成语不含 `sh`，其余 10900 个简化为只含一个 `sh`。在四个位置等概率的假设下，单次首猜 `sh` 的灰、红、绿概率可以直接计算，期望熵约为 1.008 bit。

V1 计算很快，但实测暴露了结构性错误：

- 同一元素出现两次时被当作两次独立查询；
- 移动红色的价值被低估；
- 连续铺设互不重复的新声韵元素会得到异常高分；
- `先来后到`、`瑟调琴弄` 等猜测可能远超 1000 个基准词的第一名。

结论是：问题不在于缺少一个“红色权重”，而在于逐元素相加的概率模型本身不成立。

### 4.3 V2：声母四元组后验 + 韵母四元组后验

V2 将一个维度的四个位置作为整体，使用与游戏相同的重复匹配规则，计算完整四位反馈码的熵：

\[
E_{V2}(g)=H(F_I(g,X_I))+H(F_F(g,X_F))
\]

状态中分别维护：

- 仍符合声母历史反馈的语料行 `initialRows`；
- 仍符合韵母历史反馈的语料行 `finalRows`。

V2 的重要突破是：重复元素和多个红色不再需要单独罗列情况，它们自然体现在完整反馈分组中。前文“两个 `sh` 得到 `log2 3`”的例子可以被统一算法直接算出。

V2 实际表现明显优于 V1，但它仍有两个有意的独立性假设：

- 声母与韵母相互独立；
- 不使用全拼反馈。

这会忽略合法音节和声韵连接关系。

### 4.4 V2.1：联合后验退化诊断

在正式修改评分前，开发模式额外维护了两组诊断集合：

- `ifRows`：同时满足声母和韵母历史反馈的真实语料行；
- `ifPyRows`：同时满足声母、韵母和全拼历史反馈的真实语料行。

实测结论是：

- “真实联合候选很少，但独立声母/韵母后验仍然很大”的词库稀疏现象很常见；
- `ifPyRows` 在首猜后降到 10 以下并不罕见；
- 真正连独立后验也很小的情况相对较晚、较少出现。

因此不能等到联合候选恰好为 1 才回退，也不能简单放弃声韵联合信息。

### 4.5 V3：真实候选与虚拟拼音粒子的混合模型

V3 的目标是计算真正的联合反馈熵，同时避免真实词库过稀。

它混合两类粒子：

- **真实粒子**：来自 `ifPyRows`，保留真实语料的频率权重；
- **虚拟粒子**：将当前声母后验与韵母后验重新配对，形成不要求是现实成语、但反馈统计合理的四音节假设。

混合比例由真实联合后验的有效假设数控制：

\[
\lambda=\frac{N_{eff}}{N_{eff}+32}
\]

真实联合后验丰富时，`λ` 接近 1；它变稀时，虚拟粒子连续接管，而不是在某个阈值突然切换。

虚拟粒子不是随意拼接。它们必须：

- 四个声韵对都属于语料中出现过的合法音节；
- 满足全部历史全拼反馈；
- 按全局声韵耦合比校准；
- 按真实成语中的声母、韵母、全拼重复结构校准。

V3 最初作为影子模型与 V2 并行观察。试玩显示大多数盘面结果接近 V2，少部分声韵连接关键的盘面有明显改善，因此后来成为正式中前盘模型。

### 4.6 加入声调与“实际信息量”

声调后验独立于 V3 拼音粒子。定义：

- `E1`：声母、韵母、全拼的联合期望熵；
- `E2`：声调反馈的期望熵；
- `I1`：本猜实际获得的声韵全拼联合信息；
- `I2`：本猜实际获得的声调信息。

评价分数和累计信息采用不同公式：

\[
E=E_1+w(J)E_2
\]

\[
I=I_1+I_2
\]

声调权重只影响“这次猜测有多好”，不能修改“实际公开反馈包含了多少信息”。因此 `I2` 绝不能乘 `w`。

### 4.7 V3 中前盘的零命中修正

实际反馈可能在 4096 个粒子中一次都未命中。如果直接认为概率为 `1/4096`，会把信息上限错误限制在 12 bit；如果只使用真实后验，又会重新受到词库稀疏影响。

当前采用平滑混合：

- 粒子命中 0 次时，实际概率完全使用真实 `ifPyRows` 的命中比例；
- 命中达到 8 次时，完全使用粒子比例；
- 1～8 次之间用 smoothstep 平滑过渡。

令 `h` 为粒子命中数，平滑权重为：

\[
\alpha=\operatorname{smoothstep}(h/8)
\]

则：

\[
p=(1-\alpha)p_{real}+\alpha p_{particle},\qquad I_1=-\log_2p
\]

这一处理只用于实际信息 `I1`，不改变猜前的期望熵排名。

### 4.8 末盘补全模型

V3 仍可能在信息较多时塌缩：真实/虚拟粒子都只覆盖到极少数结构，导致许多仍有价值的查询被算成 `E1 = 0`。

当前以去重后的独立后验规模乘积作为切换条件：

\[
N_I\times N_F\le 32
\]

其中 `N_I`、`N_F` 是当前声母四元组和韵母四元组的不同取值数量，不是语料行数。

进入末盘后，不再使用 V3 粒子，而是从 396 种合法音节出发，按公开反馈进行完整的约束搜索，生成所有允许的四音节组合。它们不必组成真实成语，因为模型要补全的是人类面对的拼音逻辑空间。

末盘候选的先验权重为：

\[
W(s_1,s_2,s_3,s_4)=\prod_{j=1}^{4}q(s_j)\times R_{endgame}(signature)
\]

其中 `q(s)` 是音节在 176040 个语料槽位中的全局频率，`R_endgame` 是位置对称的重复结构修正。

搜索采用：

- 各位置固定值和排除值；
- 每个元素的最少/最多出现次数；
- 约束传播；
- 优先展开候选最少的位置；
- 完成候选后重新运行精确反馈编码器。

固定预算为：

- 最多 262144 个搜索节点；
- 最多 4096 个完整候选；
- 只有搜索完整结束才允许评分。

如果超预算，当前猜测的常规评价暂停，不能使用部分候选，也不能退回已经塌缩的 V3。但真实反馈仍会更新后验，下一猜可以继续尝试。缺失的 `I1` 会被记录，累计信息被标为下界，而不是静默加零。

### 4.9 信息饱和压缩与特殊评级

纯信息熵在信息充足时仍会鼓励继续铺新元素。当前没有改变 1000 词排名方法，而是只压缩高于 Good 分界的百分位，详见第 8 节。

同时，对满足全部历史反馈的猜测和最终猜中答案的猜测设置评级下限。这不是给所有原位绿色奖励，而是在累计条件足够多时，承认玩家开始收束答案是合理行为。

### 4.10 性能版：下一猜预计算 + Web Worker

1000 个基准词排名曾占一次评价的大部分时间。现在每轮反馈更新后，Worker 会提前：

- 构造下一轮 V3 粒子或末盘后验；
- 构造声调样本；
- 计算 1000 个基准词的 `E1`、`E2`、`E`；
- 保存排序后的 1000 个总分。

玩家提交后只需计算玩家这一词的熵，并用二分查找得到严格低于它的基准词数量。评价徽章异步出现，游戏输入和按钮不等待排名计算。

## 5. 预处理数据

数据由 `scripts/generate-eval-data.mjs` 从 `playground/idioms.jsonl` 生成到 `src/eval/data.ts`。

### 5.1 紧凑表示

每条语料包含四个声母、韵母和声调：

- 声母 ID 使用 5 bit；
- 韵母 ID 使用 6 bit；
- 声调使用 3 bit；
- 四元组打包进 `uint32`；
- typed array 以小端 base64 写入生成文件，运行时懒解码。

当前生成数据包括：

- 44010 条语料行；
- 176040 个音节槽位；
- 24 类声母（含零声母）；
- 34 类韵母；
- 396 种语料支持的合法声韵组合；
- 声母、韵母、声调四元组；
- 音节、声母、韵母的全局频数；
- V3 和末盘各自使用的重复结构修正表；
- 固定种子从 44010 条语料抽取的 1000 个基准猜测。

生成器会重新解析拼音并校验拆分约定，避免 `y/w`、零声母、多音字等在生成时和运行时产生不同反馈。

### 5.2 重复结构校准

结构签名分别编码四个位置上：

- 哪些声母相等；
- 哪些韵母相等；
- 哪些完整音节相等。

V3 的基础模型来自随机重配真实声母/韵母四元组。生成器固定种子重配一百万次，比较基础模型和真实语料的签名分布，并计算修正权重：

\[
R(signature)=\frac{P_{real}+\epsilon}{P_{base}+\epsilon}
\]

权重截断在 `[1/16,16]`，避免极罕见签名主导粒子。

末盘从独立音节 `q(s)` 出发，因此使用单独校准的、对位置排列取轨道等价类的结构修正，不能复用 V3 修正表。

## 6. 反馈编码

单个维度的四位反馈是一个四位三进制数：

\[
c=s_0+3s_1+9s_2+27s_3,\qquad s_i\in\{0,1,2\}
\]

因此每个维度有 `3^4 = 81` 个桶。

编码步骤严格为：

1. 标出所有绿色，并占用对应答案槽位；
2. 对剩余查询从左到右寻找第一个未占用的相同答案元素；
3. 找到则标红，否则标灰。

零声母是答案槽位中的合法类别，但玩家猜一个零声母字时没有可见的声母查询。因此声母编码会跳过 `NULL_INITIAL_ID`，不能凭空产生绿色或灰色声母信息。

声韵全拼联合码为：

\[
c_{joint}=c_I+81c_F+81^2c_{PY}
\]

理论上有 `81^3 = 531441` 个桶。实现使用可复用桶和 touched-index 列表，只清零本轮访问过的桶。

## 7. 评价状态与后验

`EvalState` 保存：

- `initialRows`：满足全部声母反馈的语料行；
- `finalRows`：满足全部韵母反馈的语料行；
- `toneRows`：满足全部声调反馈的语料行；
- `ifRows`：满足声母和韵母反馈的真实联合行；
- `ifPyRows`：再额外满足全拼反馈的真实联合行；
- 完整公开反馈历史；
- 累计 `I1`、`I2` 及缺失次数；
- 用于确定性采样的历史哈希。

声母、韵母、声调后验分别过滤，不能因为某一条真实成语同时满足所有条件就把独立后验提前坍缩为一条。`ifRows` 和 `ifPyRows` 用于 V3 真实粒子、实际信息回退以及诊断，不取代独立后验。

每轮执行顺序必须是：

1. 根据猜前状态准备模型和基准分数；
2. 计算玩家猜测的期望信息和评级；
3. 根据真实反馈计算 `I1`、`I2`；
4. 将本轮实际信息累加到 `J`；
5. 用真实反馈过滤各后验；
6. 为下一猜预计算。

如果先过滤后评分，会把本猜已经获得的信息当成猜前已知信息，产生严重的数据泄漏。

## 8. 当前评分公式

### 8.1 中前盘 V3 粒子

当 `N_I × N_F > 32` 时使用 V3。

从 `initialRows`、`finalRows` 各自确定性 reservoir sampling，最多取 4096 个四元组。然后随机重配，并依次进行：

1. 合法音节检查；
2. 历史全拼反馈检查；
3. 声韵耦合权重；
4. 重复结构权重。

候选池最多 16384 条，最多尝试 262144 次。随后使用加权系统重采样，和真实粒子混合并确定性洗牌，最终得到 4096 个粒子。语料中的重复四元组保留重复权重。

若虚拟候选完全无法生成，可退回真实粒子；若连真实粒子也不可用，则本轮没有常规评价，不伪造分布。

### 8.2 末盘完整后验

当 `N_I × N_F ≤ 32` 时使用末盘 CSP 搜索，见第 4.8 节。候选带 `Float64` 权重，反馈熵按概率质量而不是候选条数计算。

这使“移动一个红色”和“查询一个新元素”无需人为赋权：两者造成多少反馈分组、每组概率多大，直接决定熵。

### 8.3 声调权重

令 `J` 为本猜之前累计的未加权实际信息：

\[
J=\sum(I_1+I_2)
\]

声调权重为：

\[
w(J)=0.5+0.5\operatorname{clamp}\left(\frac{J-10}{10},0,1\right)
\]

即：

- `J ≤ 10`：`w = 0.5`；
- `10 < J < 20`：线性增长；
- `J ≥ 20`：`w = 1`。

玩家和全部基准词必须使用同一个猜前 `w`。

### 8.4 基准百分位

固定的 1000 个基准词来自全部 44010 条语料，而不是当前剩余候选。对玩家和基准词使用同一批粒子、同一声调样本和同一权重：

\[
E(g)=E_1(g)+w(J)E_2(g)
\]

令严格低于玩家分数的基准词数量为 `k`：

\[
r=k/1000
\]

相同分数不算“超过”，实现使用排序数组上的 strict lower bound。

### 8.5 信息饱和压缩

定义压缩系数：

\[
t=\begin{cases}
1,&N_I\times N_F\le32\\
\operatorname{clamp}\left(\frac{J-23}{7},0,1\right),&N_I\times N_F>32
\end{cases}
\]

只压缩原始百分位高于 0.70 的猜测：

\[
r'=\begin{cases}
r,&r\le0.70\\
(1-t)r+t\times0.701,&r>0.70
\end{cases}
\]

这意味着：

- `Mistake`、`Incorrect` 和 `Average` 不会因为信息充足被进一步降低；
- 高分会随 `J=23→30` 平滑压到略高于 Good 分界；
- 进入末盘模型后，高于 0.70 的分数直接压到 0.701。

### 8.6 六档常规评价

分档使用严格 `>`，不提前四舍五入：

| 最终百分位 `r'` | 评价 |
|---:|---|
| `> 0.99` | Brilliant / 绝妙 |
| `> 0.90` | Excellent / 优秀 |
| `> 0.70` | Good / 不错 |
| `> 0.50` | Average / 一般 |
| `> 0.30` | Mistake / 失误 |
| 其余 | Incorrect / 错误 |

因此 `0.70` 本身是 Average，`0.701` 是 Good。

### 8.7 满足全部反馈与猜中答案

`matchesAllFeedback()` 会把当前猜测当作假想答案，使用游戏的完整反馈算法重放所有历史。检查包括汉字、声母、韵母、全拼、声调、位置和重复数量；这与严格模式允许什么输入不是同一件事。

满足全部历史反馈时，特殊评级下限为：

| 猜前累计信息 `J` | 评级下限 |
|---:|---|
| `J ≤ 13` | 无，回到常规评价 |
| `13 < J < 23` | Brilliant |
| `23 ≤ J < 26` | Excellent |
| `J ≥ 26` | Good |

如果本猜直接猜中答案，则 `J ≤ 13` 时也至少为 Brilliant；其它区间沿用上表。

最终评价取常规评价和特殊评级中较高者。特殊规则只能抬高，不能压低正常排名得到的等级。

## 9. 实际信息量

实际信息只影响后续猜测，不改变本猜常规期望分数。

如果观察到的反馈事件概率为 `p`：

\[
I=-\log_2p
\]

- V3 的 `I1` 使用第 4.7 节的粒子/真实后验平滑概率；
- 末盘 `I1` 直接使用完整加权候选中该联合反馈的概率质量；
- `I2` 始终遍历完整 `toneRows`，使用实际声调反馈的精确比例；
- 累计时使用 `I1 + I2`，不乘声调权重。

如果某次 `I1` 或 `I2` 无法计算，相应 `missingI*` 加一。之后显示的 `J` 是已知下界，声调权重保守使用这一下界。

## 10. Worker、恢复与持久化

### 10.1 两阶段接口

核心接口被拆成：

- `prepareEvaluation(state)`：生成粒子/末盘候选、声调样本和 1000 个基准分数；
- `advancePreparedEvaluation(state, prepared, guess, feedback)`：计算玩家分数、二分排名、实际信息并更新状态。

同步 `evaluate()`、`advanceEvaluation()` 仍用于测试和非 UI 调用；游戏页面使用 Worker 路径。

### 10.2 Worker 时序

`EvalWorkerEngine` 串行处理 `init` 和 `append`：

```text
恢复历史
  → 准备下一猜
  → ready
玩家提交
  → 只计算玩家猜测和实际反馈
  → 回传 rating
  → 准备再下一猜
  → ready
```

连续快速提交会按索引排队。`readyBeforeSubmit`、`queueWaitMs`、`playerMs`、`preparationMs` 用于判断预计算是否及时完成。

### 10.3 会话隔离

游戏标识包含模式和答案。每日、随机、自定义题切换，或同长度残局内容变化时，会终止旧 Worker 并创建新会话。

主线程同时校验：

- `sessionId`；
- 当前游戏 key；
- 猜测索引；
- 猜测文字。

旧 Worker 的迟到消息不会污染新游戏。

### 10.4 评价持久化

评级存于 `TriesMeta.ratings`，版本存于 `ratingsVersion`。当前版本是 5。

- 新猜测先写入 `null`；
- 有未完成任务时清除 `ratingsVersion`；
- 所有已提交猜测都得到结果后才写入版本 5；
- 旧版本记录会在 Worker 中逐猜重算；
- 已是版本 5 的记录可跳过历史 1000 词排名，但仍必须重放历史，以重建后验和累计信息；
- Worker 连续启动失败时，本局关闭评价，不在主线程同步回退。

显示设置只控制徽章是否显示，不能停止状态重建，否则重新开启评价时会失去后验。

## 11. 开发诊断

开发模式记录每一猜的完整轨迹：

- 声母、韵母、声调后验行数和不同四元组数；
- `ifRows`、`ifPyRows`、不同全拼四元组数和有效假设数；
- 每轮后验保留比例；
- V3 或末盘模型、候选数、搜索节点和搜索状态；
- `E1`、`E2`、`E`、`I1`、`I2`、累计 `J`；
- 声调权重、压缩系数、原始/最终百分位和特殊评级；
- V3 的真实/虚拟粒子、接受率、ESS、非法音节淘汰和结构权重截断；
- 1000 个基准词的分数列表；
- 生成、排名、玩家计算、队列等待和总耗时。

诊断标签含义：

- `none`：没有发现明显退化；
- `corpus-sparse`：真实联合词库很稀，但独立后验尚未进入末盘；
- `corpus-saturated`：`N_I × N_F ≤ 32`，表示词库后验已进入末盘触发区，不代表逻辑上没有未知信息；
- `invalid`：真实联合后验为空，通常意味着反馈/拼音约定不一致或状态损坏。

有效假设数由分布熵定义：

\[
N_{eff}=2^{H(P)}
\]

它能区分“100 条等权假设”和“100 条记录几乎都集中在同一拼音四元组”的情况。

## 12. 当前明确不做的内容

### 12.1 Lucky / Unlucky

早期设计考虑比较期望信息和实际信息，附加幸运评价。该方向已经明确放弃。主评价描述决策质量；真实反馈只用于更新后续状态。

### 12.2 汉字信息

当前 `E1` 不包含红字/绿字。汉字需要“全拼 → 汉字频率”的条件分布，并与声韵全拼强耦合；收益相对成本较低，暂不实现。汉字仍用于“满足全部反馈”特殊规则。

### 12.3 声调与拼音的联合先验

声调目前是独立后验。模型不知道例如某些声韵组合更可能对应特定声调。这是有意的近似，而不是对语言学独立性的断言。

### 12.4 语义真实的虚拟成语

虚拟粒子只追求反馈统计合理，不追求组成真实词语或符合汉语语义。要求虚拟候选都是现实成语会重新引入词库稀疏。

### 12.5 位置专属先验

音节频率 `q(s)` 使用所有位置的全局分布，不建立第一字、第二字等位置条件概率。这保持了位置对称，也控制了数据和模型复杂度。

### 12.6 严格模式专用评价

算法的设计语义是普通模式下的自由猜测，不包含“严格模式必须复用提示”的策略价值。严格模式若显示评价，也只是复用普通模式模型，尚未单独校准。

## 14. 修改算法时必须保持的不变量

1. **评分必须使用猜前状态。** 实际反馈只能影响本猜 `I` 和之后的猜测。
2. **玩家和基准词共享同一后验、粒子及声调权重。**
3. **反馈算法必须与游戏一致。** 尤其不能简化重复匹配和零声母。
4. **全拼必须与声母、韵母联合计熵。** 不能把三个熵直接相加。
5. **实际信息不乘声调权重。** `E=E1+wE2`，但 `I=I1+I2`。
6. **百分位使用严格低于。** 平分的基准词不计入超过数量。
7. **末盘搜索失败不能使用部分结果。** 部分枚举会形成不可控偏差。
8. **历史恢复不能只恢复徽章。** 后验、累计信息和下一猜预计算都必须重建。
9. **所有随机过程必须由状态派生固定种子。** 刷新和模式切换后结果必须一致。
10. **改变评分结果时升级 `EVAL_VERSION`。** 纯性能重构且数值完全一致时不升级。

## 15. 一轮评价的简化伪代码

```ts
function prepareTurn(state) {
  const J = state.information.i1 + state.information.i2
  const { initialUnique, finalUnique } = posteriorSizes(state)

  const model = initialUnique * finalUnique <= 32
    ? enumerateCompleteEndgame(state.history)
    : createMixedV3Particles(state)

  const tones = sampleTonePosterior(state)
  const w = toneWeight(J)

  const benchmarkScores = fixed1000.map((guess) =>
    jointPinyinEntropy(guess, model)
      + w * toneEntropy(guess, tones),
  ).sort(ascending)

  return { model, tones, w, benchmarkScores, J }
}

function submitGuess(state, prepared, guess, actualFeedback) {
  const E1 = jointPinyinEntropy(guess, prepared.model)
  const E2 = toneEntropy(guess, prepared.tones)
  const E = E1 + prepared.w * E2

  const rawPercentile = strictLowerBound(prepared.benchmarkScores, E) / 1000
  const percentile = compressHighPercentile(rawPercentile, prepared.J, state)
  const normalRating = ratingFromPercentile(percentile)
  const specialRating = ratingFloorForConvergingGuess(state, guess, actualFeedback)

  const I1 = observedJointInformation(prepared.model, actualFeedback)
  const I2 = observedExactToneInformation(state.toneRows, actualFeedback)

  updateStateAndPosteriors(state, guess, actualFeedback, I1, I2)
  return higherRating(normalRating, specialRating)
}
```

这段伪代码省略了 V3 的零命中平滑、搜索失败、缺失信息下界、Worker 会话和持久化保护，但保留了现行算法最重要的因果顺序。
